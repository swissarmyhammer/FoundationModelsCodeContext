title: The frame decoder must not stop or crash on a bad header
---
## Problem
- `FrameDecoder.extractNextMessage` (`Sources/FoundationModelsCodeContext/LSP/Wire.swift:116-138`) returns `nil` and removes no bytes when the header is not UTF-8 or when it has no number for `Content-Length` (`:121-126`). The decoder then waits for more bytes forever. All later messages from the server are lost, and the buffer grows with no limit. The pending requests stop only at their timeout, and the daemon does not see the problem.
- Crash: `parseContentLength` (`:144-153`) accepts a negative number. With `Content-Length: -5`, `bodyEnd` is less than `bodyStart`, and the range at `:135` stops the process with a trap.
- There is no maximum length. A very large `Content-Length` makes the decoder keep all bytes until that length arrives.
- The test mock server has its own header parser (`Tests/.../scripted-lsp-server.swift:99-103`).

## Change
- Reject a negative `Content-Length`, a value that is not a number, a missing value, and a value that is larger than `maxContentLength` (64 MiB). Reject a header that is not UTF-8.
- After a bad header, the length of the body is not known, so the stream is not in step. Do NOT read the next bytes as a header. Make the decoder give an error. Then the connection must fail all pending requests and close, so that the daemon starts the server again through its normal restart path. Log the error one time, with no payload text.
- After the error, clear the buffer, so that it does not keep the bad bytes.
- Keep one header parser. If possible, let the test mock use the same framing code.
- (The Rust code has the same missing maximum: Rust task ^1j31ywv.)

## Tests
- `Content-Length: -5`: there is no crash, the decoder gives an error, and the connection fails its pending requests.
- `Content-Length: abc`, a missing `Content-Length`, and a header that is not UTF-8: each gives an error, and the buffer is empty after it.
- `Content-Length` larger than 64 MiB gives an error before the body arrives.
- A good frame after a good frame still decodes (no change for good input).

## Acceptance criteria
- [ ] A bad header does not stop the decoder in silence. It closes the connection, and the daemon can start the server again.
- [ ] A negative or too large length does not crash the process.
- [ ] The tests above pass.
