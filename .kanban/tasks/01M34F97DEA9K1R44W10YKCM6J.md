title: The LSP layer asks for methods the server does not have, and the log hides the answer
---
Source: a SWE-bench run of FoundationModelsACPAgent on 2026-09-21. Measured with pylsp on 2026-09-22.

## What happens

On a Django clone, the agent log has hundreds of error lines, one for each Python symbol:

    [FoundationModelsCodeContext:lsp] prepareCallHierarchy failed for django/utils/tree.py:make_hashable: The operation couldn't be completed. (FoundationModelsCodeContext.WireError error 1.)

`WireError error 1` is `serverError(code:message:)`. Thus the server sent an answer, but the code and the message do not get to the log. `Index/LSPIndexWorker.swift` logs `error.localizedDescription`. For an enum with associated values, this gives only the case index.

## Cause

`pylsp` (the server of `Languages/Python.swift`) does not have call hierarchy. Its `initialize` result has no `callHierarchyProvider`. The request gives this answer:

    {"error": {"code": -32601, "message": "Method Not Found: textDocument/prepareCallHierarchy"}}

The same is true for `workspace/symbol` and `textDocument/implementation`. pylsp answers `textDocument/references`, `definition`, `typeDefinition`, `hover` and `documentSymbol`.

`LSP/Wire.swift` states the design: "this package never gates behavior on server capabilities (plan.md: 'no capability gating')". `InitializeResult` is empty on purpose. Thus the index worker asks each server for call hierarchy, for each symbol of each file.

## Cost

- The call-edge index stays empty for Python. Thus `get callgraph`, `get inbound_calls` and `get blastradius` give no result on a Python repository. A caller cannot tell this from "no callers".
- The log has one error for each symbol. This hides the real errors near it.

## Reproduction (one second, no benchmark)

    printf 'def helper():\n    return 1\n\n\ndef main():\n    return helper()\n' > sample.py

Over stdio to `pylsp`, send `initialize`, `initialized`, `textDocument/didOpen`, then `textDocument/prepareCallHierarchy` at line 0, character 4. The answer is the -32601 error above. The `capabilities` of the `initialize` result do not have `callHierarchyProvider`.

## Proposed changes

1. Keep the `initialize` capabilities. Send a request for a method only when the server advertises it. This changes the "no capability gating" decision. Record the change in plan.md.
2. When the capability is absent, use the references path that `Ops/LiveOpsExtended.swift` already documents (`lspCallersOf` / `references`). Thus the callers of a Python symbol still have an answer.
3. Log the code and the message of `WireError.serverError`. Do not log only `localizedDescription`. Also, do not log one line for each symbol. Log one time for each (server, method) pair.

## Acceptance

- [x] `InitializeResult` keeps the server capabilities.
- [x] The index worker does not send `prepareCallHierarchy`, `workspace/symbol` or `implementation` to a server that does not advertise them.
- [x] On a Python repository, `get callgraph`, `get inbound_calls` and `get blastradius` give callers from the references fallback.
- [x] A `WireError.serverError` log line shows the code and the message.
- [x] The log has a maximum of one line for each (server, method) failure.
- [x] plan.md records the change of the "no capability gating" decision.
- [x] A test with the `sample.py` reproduction above.
